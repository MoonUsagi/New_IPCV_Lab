# 第 23 章　影像擷取與串流處理

`[基礎]`　建議時數 3 小時　｜　對應舊章：**12.Streaming_Processing**

## 學習目標

1. 說出「一張圖」和「一段流」在程式結構上的差別
2. **把單張影格的演算法包成函式，再套用到整支影片**——本章核心
3. 用分段計時找出逐幀管線真正的瓶頸，而不是猜
4. 說出 GPU 與 `parfor` 在什麼條件下會**變慢**
5. 連接相機，並知道**為什麼量到的取像速率和規格上寫的不一樣**
6. 用 `VideoWriter` 錄下結果，並在檔案大小與時間之間做選擇

## 本章最重要的五課

### 1. 單幀函式與逐幀驅動要分開（第 3、4 節）

| 層 | 負責 | 不該碰 |
|---|---|---|
| `ch23_ballSegmentFrame` | 一張影格 → 找到／沒找到、在哪、多大 | 讀檔、顯示、寫檔、累積結果 |
| `ch23_ballSegmentVideo` | 迴圈、預先配置、缺口處理、顯示/錄影 | 演算法本身 |

**`Found = false` 不是錯誤，是答案。**
`singleball.mp4` 的 45 幀裡球只在 **23 幀**看得見——
其餘是還沒進畫面、滾到紙箱後面、或出畫面了。

最容易犯的錯是**只記錄找到的幀**：

```matlab
if r.Found
    centroids(end+1,:) = r.Centroid;   % ← 只有 23 列，而影片有 45 幀
end
```

這樣**永遠算不出速度**，因為你不知道相鄰兩列差了幾幀。

### 2. 先量再改，而且每改一次要重量（第 6、7 節）

| 階段 | 天真版 | 提到迴圈外 |
|---|---|---|
| **形態學（`strel` 在迴圈內）** | **3.34–3.63 ms（45–47%）** | 0.84–0.99 ms |
| 量測 `regionprops` | 2.06–2.29 ms | **1.82–2.39 ms（41–43%）← 新瓶頸** |
| 讀檔 | 0.93–1.02 ms（13%） | 1.11–1.27 ms |
| 合計 | 7.1–8.0 ms | 4.4–5.5 ms（**1.45–1.61 倍**） |

**瓶頸換人了。** 這是分段計時最重要的用途。

**讀檔只佔 13%**——「I/O 一定最慢」的直覺是錯的，
而且就算把讀檔優化到零，整體也只快 13%（Amdahl）。

### 3. 三個「課本建議」，只有一個是真的（第 7 節、練習 2）

| 手段 | 量到的效益 | 判斷 |
|---|---|---|
| **提到迴圈外** | 1.45–1.83 倍 | ✅ **真的**，而且有分段計時佐證 |
| **關掉顯示** | 顯示佔 **48–61%** | ✅ **效益最大** |
| 預先配置 | **1.27 / 0.92 / 1.12 / 0.80 倍** | ❌ **四次量測兩快兩慢——沒有效果** |

同一個設定重跑五次，**全距達中位數的 24–62%**。
「預先配置快 12%」這種數字在這個雜訊下沒有意義。

> **預先配置仍然要做，但理由是正確性（幀號對齊），不是速度。**

有狀態的物件更嚴重：`vision.ForegroundDetector` 每幀重建
**慢 10–12 倍，而且背景模型永遠學不起來——答案是錯的**。

### 4. GPU 有交叉點，也有天花板（第 8 節、練習 3）

| 百萬像素 | 加速 |
|---|---|
| 0.06 | **0.52–0.59**（比 CPU 慢） |
| 0.23 | **0.76–0.79**（還是慢） |
| 0.92 | 1.26–1.35 |
| 8.29 | **1.57–1.59（天花板）** |

**交叉點約 0.5 MPix。** 像素再多 9 倍，加速只多 18%——
因為搬運量和計算量同步成長。

練習 3 還推翻了主教材的一個說法：把 `rgb2gray`→`imadjust`→`imgaussfilt`
**三步都留在 GPU 上，加速只有 1.09–1.12 倍，比只做一步的 1.26–1.35 還差**。
因為 `imadjust` 要算直方圖，那是 GPU 的弱項。
**「有 GPU 實作」不等於「實作得快」。**

`parfor` 在這裡是純虧：**0.66 倍（比序列慢）**，而且開池就要 36.4 秒。

### 5. 相機的 fps 不是一個你能拿來設計的數字（第 11 節、練習 5）

同一台相機、同一段程式、同一台機器，**跨六次執行**：

| 解析度 | 量到的延遲 |
|---|---|
| 320×240 | 99.9 ms |
| 640×480 | **32.1 – 96.4 ms** |
| 1280×720 | 97.5 ms |
| 1920×1080 | **17.3 – 97.1 ms（10.3 – 57.8 fps）** |

**同一個解析度差 5.6 倍，而且最快的一次發生在最高解析度上。**
像素多 27 倍，延遲沒有變——USB 相機的瓶頸通常是曝光時間、
頻寬協商與像素格式，不是像素量。

唯一穩定的事實：**第一張是離群值**（229 / 452 / 503 / 1015 ms，
是穩態的 5–59 倍）。**一律丟掉。**

> **驗收規格要寫 95 百分位，不是中位數**，而且**條件要寫得比數字還長**。

## 加分題：丟幀 vs 降解析度 — 我的預期錯了

| 策略 | 設定 | 偵測到 | RMS 誤差 | 耗時 |
|---|---|---|---|---|
| 丟幀 | S=2 | **11** | 1.23 px | — |
| 丟幀 | S=5 | **5** | 2.42 px | — |
| 降解析度 | D=3 | **23** | 1.45 px | 0.094 s |
| 降解析度 | D=4 | **23** | 2.25 px | 0.092 s |

**降解析度同時給出更小的誤差、更多的樣本、更短的時間。**

我套用了第 19、20 章「下採樣吃掉小物體」的邏輯，
但**沒先量這顆球有多大**——220 像素，縮 4 倍還剩 14 像素，還在。
和第 22 章練習 1 是完全一樣的錯誤：**推理鏈正確，前提沒查**。

判準應該是：

$$D_{\max} \approx \sqrt{\frac{\text{目標面積}}{\text{可接受的最小面積}}}$$

**而且忘記把 `MinArea` 跟著 $D^2$ 縮的話，D=3 就會 0 幀——沒有任何錯誤訊息。**

## R2026a 注意事項

- **`insertText` 的預設字型 Roboto-Regular 不含中文。**
  傳中文進去每一幀都會發警告，字還畫不出來。
  影像上的標註一律用英數；非要中文得指定 `Font=`（會綁死機器）。
- **`VideoWriter` 一定要 `close`**，索引寫在檔尾，沒關就是壞檔。用 `onCleanup`。
- **`writer.FrameRate` 要自己設**，預設 30；來源 15 fps 不設就得到快轉兩倍的影片。
- **`NumFrames` 不是免費的**，某些容器要掃過整個檔案。串流用 `hasFrame`。
- **遞增的隨機存取幾乎不用錢**（實測 1.0–1.1 倍），**反向讀取才貴**。
- GPU 計時要用 **`gputimeit`**，`timeit` 量到的是「送出指令」不是「算完」。

## 換成你自己的影片

只改一支函式，介面對齊 `ch23_ballSegmentFrame`：

```matlab
function result = myFrameAlgorithm(frame)
    result = struct(Found=false, Centroid=[NaN NaN], ...
                    Area=NaN, BBox=NaN(1,4), Mask=false(size(frame,1,2)));
    % ... 你的演算法
end
```

然後複製 `ch23_ballSegmentVideo`，只換中間呼叫的那一行。

**第一件事是看 `Found` 的比例**——練習 6 把綠球偵測器套到車流影片上，
得到 120 幀中 0 幀，沒有任何錯誤訊息。**那和忘記縮 `MinArea` 的症狀一模一樣。**
